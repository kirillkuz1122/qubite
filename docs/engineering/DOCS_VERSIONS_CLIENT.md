# Версии документов: клиент DOC-004b

Контракт сервера — DOC-004a в `task/DOC-004`, решения D-811…D-816. Клиент не
меняет сервер и не добавляет экраны; панель истории и корзина остаются DOC-004c.

`httpDocsTransport()` предоставляет `listVersions(id, before?)`, `getVersion`,
`createVersion`, `renameVersion`, `deleteVersion` и `listTrash`. Список — одна
страница до 50 версий, курсор RFC3339 задаётся явно. Поля метаданных совпадают
с сервером, `ystate` на границе HTTP превращается из base64 в `Uint8Array`.
Удаление именованной версии принимает пустой ответ 204. Все методы используют
общую авторизацию, CSRF и `HttpError`, включая запреты сервера и отсутствие сети.

Для именованного снимка следует вызывать `DocStore.createVersion(id, name)`:
он сначала синхронизирует документ и требует статус `saved`. Низкоуровневый
метод транспорта, как и серверный POST, снимает текущее состояние сервера.
Возврат документа из корзины выполняется существующим `SyncClient.restore`,
снимки читаются через тот же транспорт. Удаление документа навсегда не добавлено.

`handle.restoreVersion({id, ystate})` работает без сети. Есть также
`store.restoreVersion(docId, version)`, который загружает локальный журнал,
не ожидая сетевого открытия. Создаётся временный Y.Doc, его корень Lexical
копируется в текущий корень одной транзакцией. Атрибуты XmlText/XmlElement,
маркеры TextNode в Y.Map, форматирование и UUID упоминаний сохраняются.
Старые Item и векторы текущего документа не подменяются состоянием версии.
Параллельные новые блоки сливаются как обычно; дописки в удалённые блоки
сохраняет прежний `watchLostEdits` для предложения возврата.

Байты восстановления, текст и отметка `restore` записываются в одной
транзакции IndexedDB. Отметка содержит UUID версии и поколение локальной
правки; ответ старого POST не может снять более новое восстановление,
даже из той же версии. Она переживает закрытие, перезапуск, ошибку сети
и потерю ответа. Первый POST с восстановлением передаёт `reason: "restore"`,
`restore_of`, обычные `text`, `snapshot` и `links`. При `text_stale` отметка
остаётся до успешного догона текста. Обычные правки не получают новых полей.

`renderText` и `extractLinks` должны быть заданы так же, как для обычной
фоновой отправки: в приложении это `renderDocText` и `extractDocLinks`.
При восстановлении экспорт читается из восстановленного Y.Doc, даже если
подключённый экран ещё возвращает прежний текст. Текст и связи из исторического
Markdown не подставляются вместо экспорта дерева.

Решил так, можно откатить:

- Несколько восстановлений до одной отправки объединяются журналом Yjs,
  `restore_of` указывает последний выбранный снимок. Успешный повтор POST
  после потери ответа может создать дополнительный `before_restore`, как
  предусмотрено API DOC-004a.
- `versions-diff.ts` не зависит от Lexical/DOM. `blocksFromDoc` пропускает
  служебные маркеры текста, читает вид и галочку. Упоминание представлено как
  `[@](qubite://UUID)`: разные цели различаются без исторического кэша названий.
- `diffBlocks` возвращает `{op, block}` для `equal|added|removed` и
  `{op: 'changed', oldBlock, newBlock, words}` для изменения. Якоря определяет
  LCS по виду и тексту; перестановка — удаление и добавление. Галочка учитывается
  отдельно. Между якорями близкие тексты одного вида сопоставляются по позиции;
  близость — не менее половины общей длины словесной подпоследовательности
  по коэффициенту Дайса. Для одного слова так же сравниваются символы.
  Словесные операции `equal|add|del` сохраняют пробелы и пунктуацию.
  LCS использует алгоритм Хиршберга без квадратной таблицы в памяти.

Добавлены Vitest-сценарии транспорта, IndexedDB, офлайна, повторов, параллельных
правок, пустых снимков, настоящего дерева Lexical, экспорта текста и связей,
сравнения блоков и слов. Проверки, сборки, тесты и браузер на Pi не запускались
по указанию владельца; результат должен проверить CI.
