Ревью Qubite, 11–12 ноября 2026

Проверен commit `c51c7c93a96392da91ad0f04b8cb0e46710c1916` в `/workspace/qubite`. Исходники и конфигурация приложения не исправлялись. По просьбе владельца результаты оформлены отдельным коммитом документации. Дополнительные проверки выполнялись в отдельной копии и на отдельной PostgreSQL. Исходники воспроизведений, сводка результатов и снимки сохранены рядом с этим отчётом.

Основные риски — изоляция аккаунтов в браузере, пропуск данных при синхронизации и восстановление устаревшей базы при неудачном обновлении. Ниже 11 замечаний: 9 воспроизведены локальными тестами, ещё 2 установлены по пути выполнения кода. P1 означает высокий приоритет из-за риска раскрытия или потери данных; P2 — функциональную проблему, которую следует исправить планово. Это приоритеты разработки, не оценки CVSS.

**1. P1 — Очередь предыдущего аккаунта может отправиться от имени нового.**

Клиент выбирает IndexedDB по аккаунту из `useMe`, но транспорт при каждом запросе берёт текущие общие cookie браузера. Если вкладка A осталась со старым клиентом и неотправленной записью, а другая вкладка вошла в B, событие `online` в старой вкладке отправляет очередь A с учётными данными B. Операция `create` не содержит ожидаемого владельца; сервер назначает владельцем текущий аккаунт сессии. Раздельные имена баз сами по себе этого не предотвращают.

Код: [AccountSyncProvider](../../apps/web/src/app/sync.tsx#L47), [HTTP-транспорт](../../packages/sync-client/src/http.ts#L42), [обработчик online](../../packages/sync-client/src/watch.ts#L36), [серверный push](../../crates/qubite-server/src/sync.rs#L96).

Подтверждение: Playwright с настоящим клиентом и поддельными API-сессиями зафиксировал отправку `PRIVATE-A-REVIEW` с CSRF-cookie аккаунта B. Серверное назначение владельца проверено по коду. Это сценарий переключения аккаунтов на одном устройстве, а не произвольный удалённый захват чужого аккаунта. Нужна привязка обмена к ожидаемому аккаунту с проверкой на сервере и остановка старых клиентов при смене сессии между вкладками.

**2. P1 — Курсор синхронизации может навсегда пропустить зафиксированную транзакцию.**

`events.seq` выдаётся PostgreSQL при вставке, до commit. Медленная транзакция A получает seq=1; B получает seq=2 и фиксируется раньше. Клиент получает B и сохраняет cursor=2. После commit A запросы `seq > 2` больше не возвращают её событие. Новое устройство или сброс курсора увидят объект, уже синхронизировавшееся устройство — нет, пока не появится другое событие этого объекта.

Код: [events.seq](../../crates/qubite-db/migrations/0002_core_objects.sql#L63), [вставка события](../../crates/qubite-objects/src/events.rs#L59), [pull_with](../../crates/qubite-sync-server/src/lib.rs#L420).

Подтверждение на PostgreSQL: после первого pull курсор 2; после commit A следующий pull возвращает 0 объектов, полный pull — 2. Нужен курсор, безопасный относительно порядка commit, либо протокол с гарантированным учётом незавершённых транзакций. Простая замена sequence на время или UUID проблему порядка commit не решает.

**3. P1 — Автоматический rollback обновления теряет записи после начала резервного копирования.**

Скрипт делает `pg_dump`, пока старый сервер и бот продолжают принимать изменения. Затем выполняет миграции и перезапускает службы. При ошибке миграции или проверки готовности rollback удаляет текущую базу и восстанавливает snapshot. Все подтверждённые записи после snapshot исчезают. Остановка служб выполняется только внутри восстановления — слишком поздно для сохранения этих записей.

Код: [бэкап и обновление](../../deploy/pi/update.sh#L209), [восстановление базы](../../deploy/pi/update.sh#L100), [автоматический откат](../../deploy/pi/update.sh#L221).

Подтверждение — статический разбор порядка вызовов. Реальный deploy/rollback не запускался. Нужен запрет новых записей и завершение активных операций до snapshot либо стратегия совместимых миграций и восстановления, сохраняющая записи после snapshot.

**4. P2 — Ошибка выхода из аккаунта скрывается, сессия остаётся действующей.**

Обычный `logout` перехватывает любую ошибку POST, очищает клиентское состояние и переводит на главную. Сетевой сбой или HTTP 500 ошибочно трактуются как отсутствие сессии. HttpOnly-cookie и серверная сессия при этом могут остаться: после перезагрузки пользователь снова оказывается вошедшим. На общем устройстве это даёт следующему человеку доступ к оставленной сессии.

Код: [logout](../../apps/web/src/auth/Account.tsx#L102).

Подтверждение: в браузере прерван запрос `/api/auth/logout`; интерфейс показал выход, повторное открытие `/account` снова показало авторизованный аккаунт. Нужны отдельная обработка уже отсутствующей сессии и явное сообщение о неуспешном выходе для остальных ошибок.

**5. P2 — Отклонённая правка блокирует дальнейшее обновление объекта.**

При `rejected` для существующего объекта операция удаляется из outbox, но `local.pending` остаётся `true`. `mergeSnapshot` игнорирует любые новые снимки такого объекта, одновременно продвигая общий курсор. После `dismissProblem` состояние клиента становится `synced`, хотя объект всё ещё заблокирован для обновлений. Даже без dismiss поступающие изменения объекта не применяются.

Код: [обработка rejected](../../packages/sync-client/src/client.ts#L283), [применение снимка](../../packages/sync-client/src/client.ts#L303), [расчёт статуса](../../packages/sync-client/src/client.ts#L310).

Подтверждение: тест отклоняет изменение заголовка, затем отдаёт более новую серверную ревизию; клиент сохраняет отвергнутый заголовок и `pending=true`. Нужны восстановление серверной версии/управляемый повтор операции и согласованность флага pending с реально существующей очередью.

**6. P2 — Параллельные локальные правки перезаписывают друг друга.**

`edit` читает объект вне транзакции `commitLocal`. Два одновременных изменения разных полей читают одну ревизию, формируют одинаковый `base_revision` и последовательно записывают два снимка. Второй снимок затирает поле, изменённое первым. Очередь при этом сохраняет обе операции, создавая дополнительный конфликт на сервере. Между вкладками риск сохраняется даже при последовательном коде внутри каждой вкладки.

Код: [read-modify-write](../../packages/sync-client/src/client.ts#L159), [транзакция записи](../../packages/sync-client/src/store.ts#L67).

Подтверждение: параллельные `patch(priority=high)` и `patch(status=done)` заканчиваются ревизией 2 вместо 3; итоговый локальный объект содержит только одну из двух правок. Чтение, вычисление новой ревизии, запись объекта и outbox должны выполняться атомарно с учётом нескольких клиентов IndexedDB.

**7. P2 — После выдачи доступа клиент не получает старые данные модуля.**

В pull используется один курсор для всех модулей, а фильтр `rules.readable` применяется до выбора следующего курсора. Скрытое событие модуля с seq=1 пропускается, доступное событие другого модуля с seq=2 продвигает курсор. Если позже выдать доступ к первому модулю, его старое событие остаётся за курсором. Повторная авторизация прав сама по себе не запускает начальную загрузку данных.

Код: [фильтр модулей и курсор](../../crates/qubite-sync-server/src/lib.rs#L421), [передача текущих прав](../../crates/qubite-server/src/sync.rs#L141).

Подтверждение на PostgreSQL: после расширения readable инкрементальный pull возвращает 0 объектов, полный pull возвращает оба существующих объекта. Нужны версия набора прав с повторной загрузкой либо курсоры/начальная загрузка по модулям. Это отдельная проблема от порядка commit в замечании 2.

**8. P2 — Производственная CSP блокирует локальный Whisper.**

Поддерживаемый адрес по умолчанию — `http://127.0.0.1:8080`, браузер отправляет туда `POST /inference`. В Caddy `connect-src` не разрешает этот адрес. Поэтому даже корректно настроенный Whisper с CORS не получит запрос от опубликованного сайта; интерфейс покажет сетевую ошибку и сохранит только звук без локальной расшифровки.

Код: [CSP](../../deploy/pi/qubite.caddy#L17), [адрес по умолчанию](../../apps/web/src/app/voice-local.ts#L12), [fetch](../../apps/web/src/app/voice-local.ts#L104).

Подтверждение: Chromium с заголовком из текущего Caddy выдаёт `securitypolicyviolation`, directive=`connect-src`, blockedURI=`http://127.0.0.1:8080/inference`. Нужно согласовать поддерживаемые адреса интеграции с узким списком CSP и добавить проверку самой операции распознавания, а не только открытия страницы настроек.

**9. P2 — Фокус клавиатуры выходит за пределы модального Sheet.**

Ловушка фокуса собирает все button/input и исключает только элементы с `hidden`. Отключённая последняя кнопка остаётся последней в списке, хотя Tab её пропускает. На последнем реально доступном поле перехват не срабатывает, и фокус выходит в фон. `aria-modal=true` само по себе не блокирует фон. Аналогичные пограничные случаи возможны для скрытых через CSS элементов.

Код: [Sheet](../../packages/ui/src/Sheet.tsx#L106).

Подтверждение: настоящий Sheet с полем и последней disabled-кнопкой; Tab из поля переводит `activeElement` в BODY вне dialog. Нужен расчёт фактически доступных Tab-элементов, обработка фокуса на контейнере и изоляция фона. Это влияет на клавиатурную доступность модальных форм.

**10. P2 — HTTP-запрос обрывается раньше допустимого времени AI-вызова.**

На весь роутер установлен timeout 30 секунд, а тайм-аут одного AI-вызова по умолчанию — 60 секунд. Например, `/api/v1/english/turn` ожидает работу репетитора непосредственно в обработчике. Нормальный ответ модели между 30-й и 60-й секундой уже не может быть возвращён: внешний timeout отменит обработчик и отдаст HTTP 408. При отмене после резервирования вызов остаётся `sending`, затем восстановление помечает его `unknown` с сохранением резерва. Несколько последовательных AI-этапов дополнительно увеличивают вероятность.

Код: [HTTP timeout](../../crates/qubite-server/src/lib.rs#L1090), [AI timeout по умолчанию](../../crates/qubite-server/src/ai.rs#L56), [синхронный english_turn](../../crates/qubite-server/src/english.rs#L410), [recover_stale](../../crates/qubite-ai/src/lib.rs#L1427).

Подтверждение — статический путь вызова и отмены; реальный платный провайдер не использовался. Нужны согласованные пределы времени и жизненный цикл AI-операции, не зависящий от отмены HTTP-запроса, например задача с идентификатором и получением результата отдельно.

**11. P2 — Кэш запросов предыдущего аккаунта показывается после нового входа.**

QueryClient живёт на протяжении всей работы SPA. При выходе очищаются sync-привязка и история команд, но из QueryClient меняется только `['me']`. Персональные запросы, например `['sessions']`, не содержат ID аккаунта. После штатного выхода A, входа B и перехода в «Аккаунт» новый компонент получает старый кэш A. При ошибке обновления он продолжает показывать IP-адреса, устройства и время входов A рядом с аккаунтом B. Это отдельный сценарий от отправки старой очереди в замечании 1: достаточно одной вкладки и успешного logout.

Код: [общий QueryClient](../../apps/web/src/main.tsx#L10), [очистка при выходе](../../apps/web/src/auth/Account.tsx#L29), [ключ sessions](../../apps/web/src/auth/Account.tsx#L43), [отрисовка прежних данных при ошибке](../../apps/web/src/auth/Account.tsx#L149), [смена me при входе](../../apps/web/src/auth/Login.tsx#L65).

Подтверждение: Playwright выполнил обычный logout A и login B через формы, без перезагрузки страницы. API сессий B вернул 503, а интерфейс продолжил показывать тестовый IP A `192.0.2.99`; серверный список B был пуст. [Журнал](code-review-2026-11-12/results.md). Нужны очистка/разделение персонального кэша и отмена старых запросов на границе аккаунта. В других персональных queryKey также отсутствует ID аккаунта; содержимое этих экранов отдельно в данном воспроизведении не проверялось.

Архитектура в целом соответствует модульному монолиту: общие объекты и журнал событий, централизованная политика доступа, независимые предметные модули, браузерное локальное хранилище и CRDT для документов. Разделение подходит текущему продукту. Самые существенные недостатки находятся на стыках: аккаунт ↔ транспорт/кэш, транзакция ↔ курсор, outbox ↔ локальный снимок, AI-вызов ↔ отмена HTTP, миграция ↔ rollback. Их исправление важнее переразбиения каталогов или введения микросервисов.

В просмотренных защитных механизмах есть правильные решения: Argon2 для паролей с ограничением параллельной работы, хеширование session-токенов, CSRF и проверки origin, проверки владельца и доступа к модулям, отсутствие автоматического связывания OAuth-аккаунтов только по совпавшей почте, транзакционное резервирование AI-бюджетов, ограничения файлов, безопасные заголовки и закреплённые SHA внешних GitHub Actions. Проверка не обнаружила подтверждённого универсального обхода серверной авторизации, SQL-инъекции или выполнения shell-команд из пользовательского текста. Это вывод в пределах просмотренных путей, не доказательство отсутствия иных уязвимостей.

Есть дополнительные архитектурные и эксплуатационные наблюдения без отдельного утверждения о баге. `pull_with` по очереди читает объекты и поля модулей, что создаёт N+1 запросов на больших страницах; нагрузочные измерения не выполнялись. Сборка выдаёт главный JS-chunk около 1,39 MB (428 kB gzip), стоит проверить загрузку и стоимость разбора на слабом телефоне. Само предупреждение Vite не доказывает медленный интерфейс. Большая часть браузерных проверок использует API-моки; они не проверяют взаимодействие настоящих cookie, сервера, CSP и нескольких вкладок одновременно. Отдельный набор `e2e:csp` не запускается обычным `pnpm e2e` в текущем web workflow.

По интерфейсу проверены существующие браузерные сценарии и отдельно «Входящие» при ширине 360/1440 px в двух темах. На этих снимках нет горизонтального переполнения, основное содержимое и действия видимы; заголовки корректно перекрашиваются при штатном переключении темы. Подтверждённая проблема доступности — фокус Sheet из замечания 9. Мобильная навигация преимущественно иконками может требовать проверки понятности на новых пользователях; это рекомендация UX, не установленный дефект.
