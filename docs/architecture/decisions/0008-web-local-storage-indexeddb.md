# 0008. Локальные данные в браузере — IndexedDB, синхронизация операциями

- Статус: принято
- Дата: 2026-10-17
- Задача: FND-005

## Контекст

Qubite должен работать без сети ([MC §3](../../context/QUBITE_MASTER_CONTEXT.md)): мысль, записанная офлайн, не должна теряться. В браузере есть IndexedDB (везде, включая Firefox на Android) и SQLite в WASM поверх OPFS (быстрее для сложных запросов, но тяжелее и капризнее в разных браузерах).

## Варианты

1. IndexedDB: очередь операций + локальная копия объектов.
2. SQLite WASM (OPFS) с тем же Rust-кодом, что на устройствах (`qubite-local`).
3. Без локального хранилища — только онлайн.

## Решение

Вариант 1 для MVP. Пакет `@qubite/sync-client`:
- изменение и операция пишутся одной транзакцией IndexedDB;
- очередь отправляется по порядку; потерянный ответ безопасен — сервер узнаёт операцию по `op_id`;
- конфликт не теряет правку: она сохраняется в «проблемах», на экране — серверная версия;
- честные статусы: `synced`, `saved_local`, `syncing`, `conflict`, `error`.

Протокол — Rust-crate `qubite-sync`, формат закреплён общими образцами JSON, которые проверяют и Rust, и TS. Сервер — `qubite-sync-server` (журнал `sync_ops`).

HTTP-адреса `/api/v1/sync/*` подключаются в CMD-001, когда появятся аккаунты и Policy Gate: открыть их без проверки субъекта нельзя.

## Последствия

- Поиск по локальным данным в браузере в MVP простой (перебор), полнотекстовый — на сервере.
- Desktop и Android используют SQLite через `qubite-local` (APP-001/APP-003) с тем же протоколом.
- Конфликтующие следующие правки того же объекта тоже станут «проблемами» — человек решает их по очереди.

## Как пересмотреть

Если IndexedDB окажется медленной на больших объёмах (Docs, Ink) — перейти на SQLite WASM в web, протокол не меняется.
