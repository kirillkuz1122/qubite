# 67. Харнес 2.0: тратить меньше лимитов, меньше нагружать владельца (27.10.2026)

Индекс всех решений — [DECISIONS.md](../DECISIONS.md).

Пока только решения и мозговой штурм. Переделку делаем после сброса лимитов (HAR-001), после исследования, как это устроено у других.

| # | Решение | Статус | Источник |
|---|---|---|---|
| D-583 | **Перестраиваем харнес.** Сейчас слишком много лимита уходит на чтение документов: новая сессия набирает 100–150k контекста ещё до кода. Начинаем с харнеса внутри Qubite, но складываем его в отдельную папку, чтобы потом скопировать шаблоном в другие проекты. Общий харнес для всех проектов — позже. | CONFIRMED | [CL] |
| D-584 | **Три уровня:** менеджер (раздаёт задачи и принимает результат, код и логи не читает) → ведущий задачи (одна сессия на задачу) → помощники. Ведущий читает только свою карточку и паспорт своего модуля, а не весь DECISIONS/TASKS/STATUS. Какая модель на какой роли (Opus или Sonnet), решаем по сравнению на реальных задачах: владелец сомневается, что Sonnet справится. | CONFIRMED | [CL] |
| D-585 | **Автономия:** владельца спрашиваем только про Raspberry Pi и сеть, удаление данных и крупное направление продукта. Остальное агент решает сам и записывает «решил так, можно откатить». Деньги — не вопрос: платёжных данных у агента нет. Правило «вопросы перед каждой задачей» заменяем этим. | CONFIRMED | [CL] |
| D-586 | **Отчёты владельцу — наглядные страницы, а не простыни текста:** что сделано, скриншоты, решения, «проверь 3 пункта». Пока это Artifact (видно в приложении Claude); позже, возможно, раздел с датами на qubiteapp.online. | CONFIRMED | [CL] |
| D-587 | **Лимиты:** недельный лимит ≈ 9 полных 5-часовых окон, 10% 5-часового окна ≈ 1% недельного. 10% недельного остаётся владельцу на чат и ежедневные сводки. Со слов владельца (видел в коде), дороже выходит при 4 и больше параллельных сессиях и при контексте больше ~150k. | CONFIRMED | [CL] |
| D-588 | **Работа через окна лимитов по будильникам:** время ставим в UTC, у владельца UTC+5. Проверка 27.10: будильник в 20:10 UTC сработал с опозданием на 3 минуты, но в сессию его не пустило («нет доступа»). В новой сессии будильник на 20:18 UTC сработал точно в срок. Значит, будильники работают, а не пускает только в эту старую сессию менеджера. В HAR-001 менеджер переезжает в новую сессию. Запасной вариант — запланированная задача, которая каждый раз открывает новую сессию. | CONFIRMED | [CL] |
| D-589 | **Другие модели:** ChatGPT по подписке владельца (Codex) — независимое ревью и второй взгляд; им же проверяем, как модель понимает промпты. Muse 1.3 не используем (решение владельца 27.10 после исследования). ChatGPT — не только ревьюер, но и вторая рабочая сила: у Codex свои лимиты, чат ChatGPT без лимита. Как делить работу между Claude и Codex, решаем в HAR-001 опытом. Идеи с YouTube (подложенные баги для проверки ревьюера, самообучение скиллами) не принимаем на веру, а проверяем. | CONFIRMED | [CL] |
| D-620 | **Raspberry Pi можно использовать как сервер** для того, чего нельзя сделать в облаке (владелец, 27.10). Тяжёлые сборки и тесты — только в облаке и CI, Pi их не выдержит, памяти мало. Сервисы владельца не ломать (D-564). | CONFIRMED | [CL] |
| D-621 | **Код, который написал Codex, Claude проверяет всегда, без исключений.** Код Claude проверяет Codex. | CONFIRMED | [CL] |
| D-622 | **Проверка безопасности — раз в неделю или когда наберётся пачка заметных задач.** | CONFIRMED | [CL] |
| D-623 | **Codex работает на Raspberry Pi, а не в облаке OpenAI** (владелец, 27.10): `@codex` из GitHub не увидел окружение, тест — issue #3. Схема без входящих портов, как автодеплой (D-566): на Pi таймер в `qubite.slice` с низким приоритетом опрашивает GitHub Issues с меткой `codex` и для каждого запускает `codex exec` в отдельной копии репозитория. Модель и уровень рассуждения задаются меткой. Результат — ветка и PR. На Pi ничего не собирать и не гонять тесты: только лёгкие проверки, полные тесты — CI. Код Codex проверяет Claude (D-621). Вход в ChatGPT лежит только на Pi. | CONFIRMED | [CL] |
