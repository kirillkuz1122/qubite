## КРИТИЧЕСКОЕ УТОЧНЕНИЕ владельца — интерфейс, роли и деньги

**Прочитай `QUBITE_ACCESS_AND_OWNER_CONSOLE.md` до проектирования Identity/Admin.** В новой платформе owner пользуется **обычной главной и пользовательским UI**, а системное управление расположено отдельно, в «Настройки → Управление Qubite» и доступно только ему. Турнирные роли **не переносить** в глобальную модель Qubite: `organizer`, `moderator`, `tournament admin` существуют исключительно внутри отдельного модуля `Qubite Tournaments`, убранного из основного UX. Система регистрации **не выдаёт** доступ ко всем модулям и **никогда автоматически не открывает платные AI-модели и токены**. На старте нет тарифов/подписок, все доступы, квоты и бюджеты устанавливает owner вручную. Независимые настройки/гранты нужны для каждого модуля, сервиса, агента, AI-модели и интеграции. Проверь запреты серверными автотестами, в том числе прямые API-запросы и параллельный расход средств.

## 1. Что есть сейчас и что необходимо сохранить

По публичной документации текущий Qubite — большой рабочий MVP на HTML/CSS/JavaScript + Node.js/Express + SQLite, а не React/Next-приложение. Есть турниры, задачи, участники и команды, рейтинги, аналитика, регистрация/вход, owner/admin/moderator/organizer, Telegram-бот, администрирование, deploy-скрипты, а также сервисы поиска, Writing/LanguageTool, VPN/proxy, AliasVault, Kwork, Specbot, MCP и др. Части системы могут быть реализованы лишь частично — всё проверить. Важные крупные файлы: `back/server.js`, `back/src/db.js`, `front/js/app.js`, `front/js/api.js`. Не считай этот перечень полным.

**Продуктовое решение:** старый Qubite для турниров становится **Qubite Tournaments**, одним из модулей нового Qubite. Турниры НЕ удалять и НЕ переписывать сразу. Убрать их из основной навигации новой платформы, оставив доступный модуль Tournaments для пользователей с соответствующим доступом. Сохранить или корректно мигрировать пользователей, роли, команды, задачи, результаты, рейтинг, историю, организаторские/модераторские контуры, Telegram-функции, API и ссылки.

Основной Qubite теперь будет единым рабочим пространством с собственным новым дизайном, единой навигацией и **скрытой от обычных пользователей Owner Console в системных настройках**, которая управляет аккаунтами, разрешениями, настройками модулей, интеграциями, AI-провайдерами, квотами и аудитом. **У owner такая же пользовательская главная, как у всех; не делать owner-панель стартовой страницей.** Админка турниров остаётся **исключительно внутри Tournaments**. Глобальный owner и турнирные organizer/moderator/admin — не одинаковые полномочия. Разработай scoped RBAC/ABAC + entitlement/budget gating и правила миграции старых ролей, не расширяя права пользователей по умолчанию.

Существующая авторизация может быть повторно использована или заменена после обоснования. Сейчас аккаунтов мало, но даже при одном аккаунте нельзя без подготовки уничтожать таблицы пользователей, хеши паролей, сессии, service grants и историю. Разработай проверяемую миграцию и откат; старые URL и сервисы должны функционировать в переходный период.

Не строить новую платформу на базе Memos или Vikunja: владелец хочет собственные Docs/Planner, а не оболочку над этими приложениями. Текущие Qubite Search, Writing, VPN, Vault, Kwork, Telegram и другие части оцени на предмет **сохранить как отдельный модуль / адаптировать / мигрировать / заменить позже**. Ничего не удалять автоматически.

## 2. Целевой продукт и архитектурные принципы

Принципы из master-контекста обязательны: единая модель связанных объектов и граф знаний; AI-first, но не AI-only; красивый минималистичный адаптивный интерфейс; web + Android + позднее desktop; local-first и синхронизация; self-hosting на Raspberry Pi; переносимость данных; глобальная Timeline, версии, сравнение и восстановление; совместная работа с правами доступа; плагины и собственный MCP.

Модули: Core/Identity, Admin, Docs, Ink, Planner, Calendar, Projects, School/Homework, Learn, Knowledge/Atlas, Search/Command, Inbox/Notifications, Teams, Life/Private Journal, Finance, Focus/Guardian, Studio, Writer, Pulse/Automation, AI Intelligence/Agents/Memory/Skills, Extensions/MCP, Tournaments и legacy-сервисы. Описание и полный набор требований — **в master-контексте**, здесь это только ориентир.

Отдельно спроектируй **AI-память и навыки в стиле Hermes**: область видимости personal/project/team/task; устойчивые воспоминания с происхождением, уверенностью, редактированием и удалением; управляемый каталог skills и инструментов; создание и предложение навыков агентом с проверкой и разрешениями; работа с Hermes без принудительного запуска тяжёлой модели на каждое действие. Разграничение доступа enforce на стороне API/tool layer. Личный дневник не попадает в общий/team/RAG-контекст без явного разрешения.

Архитектура: сначала сравнить хотя бы два практически реализуемых пути (например постепенное выделение существующих модулей через strangler pattern и отдельное новое ядро с адаптером для legacy). Выбрать рекомендуемый путь с trade-offs, планом миграции, совместимостью API, стоимостью сопровождения и рисками Raspberry Pi. Рассмотреть PostgreSQL + pgvector для нового core, но не делать мгновенной необратимой замены рабочей SQLite. Уточнить необходимость отдельных фронтенда, API, нативного Ink и worker. Не создавать микросервисы ради названий модулей.

## 5. Этап 3 — план и backlog как система задач

Разбей работу не на абстрактные огромные фазы, а на **маленькие задачи**, каждая из которых может быть выполнена одним ограниченным циклом AI-агента. Каждой задаче нужны:

- ID, название, причина, модуль, приоритет и зависимости;
- конкретные файлы/контракты, на которые она влияет;
- проверяемый результат и acceptance criteria;
- обязательные автоматические тесты и команда их запуска;
- риски безопасности и данных, migration/rollback если применимо;
- критерии готовности и ссылка на коммит/PR по выполнении.

Состояния: `backlog → ready → in_progress → review/testing → done` плюс `blocked`. Сохраняй прогресс и решения в Git, чтобы новый агент без переписки мог понять, на чём остановились. Проекты не должны терять контекст между сессиями.

Первыми должны быть: аудит и baseline, тесты и CI для критичного legacy, документация миграции, **Owner Console + default-deny permissions + AI cost guard с негативными тестами**, безопасный фундамент нового интерфейса, один полезный end-to-end сценарий (создать заметку → связать → синхронизировать → найти → изменить → восстановить). R&D качества Ink на планшете отдельно и параллельно. Перенос турниров — по частям, после фиксации регрессионных тестов.

## 6. Этап 4 — Engineering Harness для разработки по задачам

Нужен **harness для Codex/Claude**, который позволяет агенту продолжать работу по backlog без постоянного ручного пересказа контекста:

1. При старте читать master-контекст, текущее состояние, AGENTS/CLAUDE, ADR, backlog и последний отчёт.
2. Выбирать следующую `ready` задачу с выполненными зависимостями, не более одной основной задачи за цикл.
3. Создавать/менять код, документацию и тесты только в объёме задачи. При существенном архитектурном отклонении — остановиться и запросить решение.
4. Запускать форматтер/lint/typecheck, unit, integration, e2e по затронутым модулям, затем необходимые регрессионные проверки. Фиксировать реальные результаты, логи без секретов.
5. Проверять, что не повреждены старые турниры, авторизация, администрация, сервисы, деплой.
6. При успехе обновить TASKS/ROADMAP/ADR/CHANGELOG/документацию, создать небольшой осмысленный коммит на русском, выполнить `git push` в согласованную ветку; при провале не помечать задачу выполненной и не пушить сломанный код.
7. При необходимости GitHub Actions должны автоматически запускать тесты на каждом push/PR. `git push` **не равен** деплою. Production deployment — отдельно, только после проверок, backup и явного разрешения; без самовольного рестарта live-сервисов.
8. После цикла оставлять компактный `handoff`: что сделано, что проверено, коммит, известные проблемы, следующая задача.
9. Внешние API, платные модели, Hermes, инструменты и автоматизации имеют лимиты стоимости, времени и шагов. Никаких бесконечных рекурсивных агентных циклов.
10. Защита от случайных правок: `git status` до и после, резервные копии перед миграциями, отсутствие `force push`, `reset --hard`, уничтожения БД и коммитов секретов.

Учти, что существующий `AGENTS.md` может предписывать прямой push в `main`. Не меняй молча рабочую Git-политику: изложи риски; для большой миграции предложи отдельную ветку/PR, согласуй стратегию, затем пушь после каждой завершённой задачи по принятому правилу. CI и автодеплой не должны автоматически разрушать production.

Не пытайся построить огромный автономный оркестратор сразу. Сначала минимальный надёжный цикл из файлов задач, git hooks/скриптов и CI; расширять его по результатам использования.

До получения ответа веди открытый реестр предположений и делай безопасную работу, не блокируемую этими ответами. Не задавай вопросы, ответы на которые уже есть в master-контексте или коде.
