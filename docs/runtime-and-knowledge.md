# Независимый вход, управление сервисами, Memos и Vikunja

## Qubite Auth

`https://qubiteapp.online/auth` — отдельная страница входа: фон и формы Qubite, без лендинга. Она переиспользует действующие формы и обработчики логина, регистрации, восстановления, CAPTCHA, OAuth и входа по коду. Вход по коду сохраняет прежнюю турнирную семантику: универсальные коды для любых сервисов пока не реализованы.

На Raspberry приложение разделено на процессы:

| Процесс | Назначение |
| --- | --- |
| `qubite-platform` | Основной сайт, турниры и административный интерфейс |
| `qubite-auth`, 127.0.0.1:9131 | Вход, сессии, разрешения сервисов, Writing и его API |
| `qubite-control-bot` | Telegram-бот управления, работает независимо от основного сайта |
| `qubite-runtime-manager` | Привилегированный менеджер фиксированного списка процессов через Unix socket |

Это вход для собственных приложений на общем домене: браузер получает Secure/HttpOnly сессию Qubite, сервис проверяет её на Auth и получает разрешения. Пароль не передаётся приложению, токен не помещается в URL. Это **не универсальный OIDC/OAuth-провайдер** для произвольных сторонних приложений. Разрешены возвраты только на точно настроенные origins; чужие адреса и циклы `/auth`/`services/return` отклоняются.

Caddy отправляет `/auth`, `/api/auth/*`, сервисные API, Writing и их ресурсы в Auth, остальной основной сайт — в platform. Когда platform выключен, корень сайта перенаправляет на Auth; после входа отображается список разрешённых сервисов. Поиск проверяет аккаунт через `QUBITE_INTERNAL_URL=http://127.0.0.1:9131`. Cookie зависит от `SESSION_COOKIE_DOMAIN`; отдельные несвязанные домены так не подключить.

Локальные сообщения между ботом и platform проходят через Unix sockets `events-bot.sock` и `events-platform.sock` рядом с SQLite, права 0600. Сохраняются уведомления о критичных действиях и ответы поддержки/SSE. Если platform выключен, веб-поддержка также выключена; Telegram и постоянная БД продолжают работать. Канал событий не является долговечной очередью.

## Выключение сервисов

В личном диалоге владельца с Qubite: `/power` или кнопка **Питание сервисов**. Статус читается из systemd/Docker; на изменение требуется одноразовое подтверждение, привязанное к сообщению, срок 2 минуты. Можно управлять Qubite, Hermes, AliasVault, LanguageTool, OmniRoute, SearXNG, панелью Hermes, поиском, Brief, Memos/Vikunja, процессами Kwork и транскрипции.

Auth, управляющий бот, менеджер, SSH, Docker daemon и сетевые службы исключены из списка. Произвольные команды/имена unit не принимаются. Доступ к root-менеджеру — только UID Qubite через `/run/qubite-runtime/manage.sock`; его исполняемый файл установлен root-owned в `/usr/local/lib/qubite/`. Это доверенная локальная граница: процессы одного UID имеют также доступ к его БД/секретам, она не изолирует приложения друг от друга.

Systemd unit отключается вместе с автозапуском, включение его восстанавливает. Контейнеры используют `unless-stopped`: остановка сохраняется при перезапуске Docker. Базы/тома при выключении не удаляются. Для Qubite также меняется `workspace_enabled`. OmniRoute пока выключен; данные сохранены. Отключение SearXNG лишает поиск источников; отключение LanguageTool — обычной проверки; предупреждение показано до подтверждения.

## Memos / Vikunja

- Заметки: `https://memos.qubiteapp.online` — Memos 0.31.0, один ARM64 контейнер, SQLite, встроенный интерфейс.
- Задачи: `https://vikunja.qubiteapp.online` — Vikunja 2.7.0, один ARM64 контейнер, SQLite, встроенный интерфейс. Почта/почтовые напоминания не настроены.

Внешняя проверка Qubite → собственный вход приложения: владелец сознательно выбрал отдельные нативные аккаунты. Созданы аккаунты `kirill`; пароли передаются владельцу лично и хранятся только в приватном файле на Raspberry. Регистрация обеих приложений закрыта. У нативных приложений сохраняются собственные сессии; выход из Qubite закрывает внешнюю проверку, не удаляя нативную сессию.

Для друга: Qubite → Админка → Пользователи → выдать Memos/Vikunja (либо `/service_user <логин>` в боте). Это разрешение на открытие сайта, **не создание нативного пользователя** и не доступ к вашим данным. В Memos администратор создаёт пользователя и приглашает в выбранное пространство. В Vikunja пользователя создают через CLI контейнера, например `docker exec -it vikunja /app/vikunja/vikunja user create -u friend -e friend@example.org`: пароль вводится интерактивно, без аргумента `-p` и shell history. Затем выбранный проект расшаривают штатными средствами. Не открывайте глобальную регистрацию ради одного друга.

Файлы данных текущей Raspberry:

- `~/services/memos/data` → `/var/opt/memos`;
- `~/services/vikunja/db` → `/db`, `~/services/vikunja/files` → `/app/vikunja/files`;
- `~/services/knowledge-private.json` — приватные учётные данные, права 600, вне git;
- маршруты Caddy: `/etc/caddy/qubite-knowledge.caddy`, Cloudflare: `~/.cloudflared/config.yml`.

Перед переносом/обновлением сохранять SQLite вместе с WAL/SHM согласованным backup или при остановленных контейнерах, а также вложения. Наличие контейнера не заменяет резервную копию.

## Hermes

`integrations/qubite-knowledge/server.py` — stdio MCP-мост к локальным штатным MCP API. Схемы берутся из файлов `memos-tools.json` / `vikunja-tools.json`, полученных из `tools/list` установленной версии. Сами схемы не содержат пользовательских записей. В конфиг Hermes добавлен `mcp_servers.qubite_knowledge`; ключи только в `~/.hermes/.qubite-knowledge-tokens.json` (600), не в skill и не в текстах ответов.

- Memos: обычный пользователь `hermes`, пространство **Кирилл и Арчи**, куда приглашён владелец. Приватные заметки `kirill` вне этого пространства Hermes не видит.
- Vikunja: отдельный ограниченный API key владельца, чтение/создание/изменение задач и проектов. Нативный key ограничивает операции, но не отдельный проект: агент видит доступные владельцу задачи. Для дополнительной изоляции нужен отдельный пользователь.
- Мост выдаёт 15 инструментов: чтение/создание/изменение заметок и задач, чтение пространств/проектов, создание/изменение проектов. Удаление, управление пользователями/ключами и изменение общего доступа отсутствуют.
- Skill установлен в `~/.hermes/skills/qubite-knowledge/SKILL.md`; исходник рядом с мостом. Он требует уточнять неоднозначные сроки, читать объект перед изменением, не отмечать задачи выполненными без запроса.

Отключённый сервис возвращает понятную ошибку; агент не должен самостоятельно включать его или придумывать успешную запись.

## Переменные и установка

`QUBITE_PROCESS_ROLE=platform|auth|bot`, `AUTH_PORT`, `RUNTIME_MANAGEMENT_SOCKET`, `SERVICES_MEMOS_BASE_URL`, `SERVICES_VIKUNJA_BASE_URL`; необязательный `QUBITE_EVENT_SOCKET_DIR` меняет каталог локальных событий. Обычный запуск без PROCESS_ROLE сохраняет прежний встроенный бот. На production нельзя одновременно запускать встроенный polling и `qubite-control-bot` с одним токеном.

`deploy/services/runtime.py` устанавливает независимые unit и root-owned менеджер. `deploy/services/caddy_merge.py:portal_routes` формирует разделённые маршруты Auth/site. Включение Memos/Vikunja не означает, что общий установщик автоматически создаёт их нативные аккаунты или выдаёт Hermes ключи: это отдельная операционная настройка.

## Ресурсы и ограничения

На Pi 5 / 4 ГБ эти два приложения выбраны без Redis/PostgreSQL. Anytype сейчас не устанавливается: Redis нельзя просто заменить SQLite, синхронизация и расшифрованный клиент добавляют отдельный расход. Живые цифры — в операционном отчёте владельца, а не обязательные минимумы проекта.

В текущем ядре Raspberry отсутствует memory cgroup. `MemoryMax`, `mem_limit` и Docker stats не доказывают работающие ограничения памяти. Проверка старта и небольшой CRUD-тест не являются нагрузочным тестом одновременной транскрипции/поиска.
